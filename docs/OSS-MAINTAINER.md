# Open-source maintainer and ecosystem case

This page gives reviewers a concise, evidence-backed view of why the project is
maintained, what is already working, and where maintainer tooling helps. It does
not treat Stars, page views, or unverified statements as adoption.

## Why the project matters

UFI001B is a low-cost Qualcomm MSM8916 portable Wi-Fi platform for which public
hardware information and safe, reproducible firmware paths are fragmented.
Users otherwise risk relying on opaque prebuilt images or procedures that do not
clearly separate the two intended write targets from modem, NV/EFS, calibration,
bootloader, and other protected partitions.

The repository turns that fragmented work into a reviewable public pipeline:

- pinned OpenWrt, feed, tool, OpenClash, and Mihomo inputs;
- a machine-readable p12/p14 partition policy;
- reproducible build metadata, package manifests, SHA-256 checksums, and SPDX
  SBOM output;
- static checks that reject private keys, private firmware, and dangerous image
  types from source control;
- documented recovery, read-back verification, and hardware-in-the-loop checks.

The work is useful even at small scale because a mistake can erase
device-unique radio data or make inexpensive hardware difficult to recover.

## Maintainer workload and use of Codex

The project uses Codex as a maintainer aid for repository-wide documentation
reviews, CI and release inspection, safety-policy consistency checks, and the
preparation of focused changes for human review. The maintainer remains
responsible for flashing decisions, secret handling, hardware tests, and final
release approval.

Additional capacity would be used for recurring open-source work:

1. triage hardware reports while removing device secrets from public context;
2. review dependency-update pull requests and source-lock changes;
3. compare source, documentation, CI policy, and release notes for drift;
4. extend static tests around partition and private-firmware boundaries;
5. turn reproducible bug reports and HIL observations into small reviewable
   patches.

No claimed user count, test result, or security property is generated by Codex
without a public record or maintainer verification.

## Near-term roadmap

- obtain independent field reports using the existing structured Issue form;
- produce a signed branch build and provenance-backed release asset;
- keep dependency automation green and review updates through pull requests;
- document additional UFI001B hardware revisions only when supported by
  reproducible evidence;
- continue improving recovery guidance without expanding the allowed write
  boundary.
